# 事故记录：线稿的两个"匹配对照"其实是同一个对照，且墨量匹配从未成立

**日期**：2026-11-24 · **状态**：已修复并重新生成 · **影响范围**：线稿数据集的全部 4 个单元（4×1349 张）

---

## 1. 摘要

线稿方向要求每个方法配一个**墨量匹配的对照**，用来排除"更淡的图 = 更好的图"这个混淆。三个单元生成后，builder 自报"总墨量匹配误差 0.0000%、前景墨量匹配误差 0.0000%"。

**但这两个数字都是假的。** 从保存下来的图片独立复算后发现：

| 检查项 | builder 自报 | 从保存图片复算 |
|---|---|---|
| 总墨量匹配误差 | 0.0000% | **28.4%** |
| 前景墨量匹配误差 | 0.0000% | 0.0000% |
| 两个对照是不同图片吗 | 未检查 | **40/40 完全相同（逐字节）** |

也就是说：两个"不同的"对照其实是**同一张图**，而总墨量匹配**从未成立**。如果这些数据被拿去训练，两个对照会给出完全相同的性能差异，"对照"这一环形同虚设。

---

## 2. 三个独立的缺陷

### 2.1 `rescale_ink` 的文档与实现不符

`rescale_ink` 的文档写着：

> With `target_foreground` only the object's outline is scaled and the background lines are left alone.

而实现是：

```python
factor = target_foreground / inside
scaled = drawing * factor          # 整幅图乘同一个因子
```

背景线同样被缩放了。结果：**两个对照的求解结果完全相同**，两个参数化退化成同一个。

### 2.2 渲染丢弃了权重

`render()` 里对照分支的最后几行是：

```python
picture = np.full_like(image, 255)
drawn = scaled > 0.05
picture[drawn] = (image[drawn].astype(np.float32) * 0.25).astype(np.uint8)
```

这里用的是 `draw_line_art` 返回的 **`scaled` 强度图**，但图片的暗度被写死成 `原图 × 0.25` —— **强度图算出来只用来决定"哪里有线"，没用来决定"线有多黑"**。于是无论求解出什么样的权重，图片都一样。

这是最隐蔽的一个：权重求解的数值完全正确（`fg_w=0.7398` vs `fg_w=0.9977`），墨量统计也完全正确，只有**图片**是错的。

### 2.3 墨量的两套定义不一致

- **builder 的定义**：`ink_masses(strength, mask, foreground)`，即 strength 图上被画到的像素的 strength 之和
- **图片的实际暗度**：`image × (1 - 0.75 × strength)`，取决于**原图颜色**

两者只成正比的前提是原图颜色恒为白，而线稿画在彩色照片上。所以**从图片复算的墨量与匹配时用的墨量不是同一个量**，偏差高达 18–28%。

---

## 3. 为什么 builder 的自检没有发现

builder 在生成后复算墨量，用的是**自己刚算出来的 `scaled` 强度图**，不是从保存的图片读回来的：

```python
new_total, new_inside = ink_masses(scaled, drawn, object_mask)
```

一个"算完 A 再用 A 的中间结果验证 A"的检查，**只能验证算术，不能验证实现**。它无法发现 2.2（图片与强度图脱节），也无法发现 2.3（两套墨量定义）。

**教训：对照的有效性必须从训练实际读到的文件上验证，不能从生成器的中间变量验证。**

---

## 4. 修复

| 缺陷 | 修复 |
|---|---|
| 2.1 | 新增 `solve_ink_weights()`，分别求解前景权重与背景权重，而不是整幅缩放 |
| 2.2 | 新增 `render_from_strength()`，图片暗度由 strength 决定，与强度图严格对应 |
| 2.3 | 渲染改为**暗度直接编码 strength**（白纸 + 灰度线），使墨量可从图片精确还原 |
| JPEG 量化 | 线稿改存 **PNG**：JPEG 的色度抽样会改变笔画暗度，而这正是对照所匹配的量 |
| manifest 风格列 | 线稿无风格概念，风格列填 `none`（与 `duplicate`/`nonstyle` 一致），否则公平性检查会把类别名当风格名 |

另外把 `draw_line_art` 的 `gate=False` 分支从"所有线同暗度"改为"前景权重 / 背景权重可分别指定"，这是两个对照能够分化的前提。

---

## 5. 验证

新增两个脚本，都**只读保存下来的文件**：

- `test_line_art_controls.py` —— 渲染后即时验证（迭代用）
- `measure_line_art.py` —— 从保存的 PNG 复算墨量并验证两个对照确实不同

修复后的结果：

```
  mean total-match error:     0.0000%
  mean foreground-match error: 0.0019%
  the two controls identical on 0/8 images
```

以及从保存图片独立复算（`measure_line_art.py`，60 张）：

| 单元 | 总墨量 | 前景墨量 |
|---|---|---|
| `line_attn` | 10801.3 | 8742.6 |
| `line_attn_vote` | 12426.9 | 7577.6 |
| `line_plain_total` | **10801.3**（匹配总墨量） | 6427.5 |
| `line_plain_foreground` | 15160.4 | **8742.7**（匹配前景墨量） |

两个对照现在**各自精确匹配不同的量**，且是**不同的图**。

---

## 6. 方法论教训

1. **自检必须从文件读回，不能用中间变量。** builder 的 "0.0000% 误差" 是自证的。
2. **两个对照必须验证"是不同的图"。** 同一张图的两个名字，会给出完全相同的性能差异，看上去一切正常。
3. **匹配所依据的量，必须与模型实际看到的量一致。** 匹配 strength 而渲染成 `image×0.25`，就是在匹配一个模型看不到的量。
4. **有损格式不能用于匹配。** JPEG 会改变笔画暗度；线稿改存 PNG。
